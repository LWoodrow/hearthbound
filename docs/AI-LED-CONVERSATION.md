# AI-led NPC conversation: deployment design

## Decision

### Task-specific context isolation (2026-10-17; local experiment, semantic gate FAILED)

The user supplied a second human failure: old button anecdote → greeting → brass choice → invitation to tell still never produces the requested tale. `--layout-probe=task-isolated` now separates interpreting PLAYER requests from factual and fictional writing material. The two-call baseline is unchanged unless this explicit variant is selected. No production import/selection, new model, extra judge or keyword response patch is enabled.

The interpreter receives eligible fact IDs and authored subject/domain labels (not fact bodies), participant roles, recent player requests and the latest ordinary NPC offer. Prior generated fictional prose and previous model-written task summaries are excluded; they were competing with the new utterance. The latest speech is its own final user message. AI chooses greeting/fiction/revision/ordinary/clarification/repeat/close and relevant source IDs. All IDs must still be currently available; no private/guarded source is added by guessing. `factSubjects` mirrors the filtered public fact ordering, not a new source of authority.

Creative writers receive voice/traits and the chosen task/preferences, not the person's family, anecdote, world or quest context. Only a revision receives the latest tagged fictional payload. Greeting writers receive no prior prose/factual records, and stale choices clear once the AI selects greeting. Factual writers receive only selected current records plus whether the last utterance was fiction, not the story itself. References to real names can still leak through a bad model-written goal; this is not a semantic guarantee that fiction contains no real people. Wrong mode selection remains possible even though context supply is deterministic. The ordinary-only diagnostic still cannot replace runtime guarded-read/social-goal orchestration.

Added regressions verify actual source exclusion and stage boundaries, factual subset selection/unknown-ID rejection, revision-only payload, roles, no prior tale/summary in interpretation, and actual memory-only dispatch. The evaluator can write a full non-overwriting JSON report with --report=<path.json>; source packets/real saves are not dumped. Current code passes529 regressions/build/four adventure validators.

Live outcomes on unchanged Huihui are not sufficient for release. Exact seeded brass initially progressed to prose, recognised fiction and returned known food venues (3 turns, median2.602s). A request-only romance run retained romance and grand scale and selected a factual food answer (6 turns, median3.529s), but still confused roles and invited needless clarification. Held-out Selka materially revised a funny ending and acknowledged fiction (4 turns, median3.607s), but stalled at a clear practical question. A FINAL five-turn greeting/brass run revived the old story on a greeting, misread brass and treated a food question as fiction (median3.319s). No state changes/checks or model/settings changes occurred. This disproves any claim that context separation alone fixes current-turn priority. Save all reports, including failed intermediate variants; do not deploy based on the attractive brass example. Next unsolved design point is intent/task-lifecycle reliability, not missing biography.

### Thread/prose agreement follow-up (2026-10-17; evaluation ONLY)

Invalid stage output is invalid-output, not an AI connection outage. `evaluateDialogue` instruments each underlying inference, exposing accurate call/timing/prompt budgets separately from the production session wrapper's outer call count. Do not claim a one-call result because that outer wrapper was invoked once. Ordinary-only probes do not implement guarded reads or social goals; runtime authored first-refusal and capability checks remain untouched. It must not be adopted as a general replacement dispatcher.

Five focused regressions cover compact source/tool/history preservation, single-mode kind/move mapping, writer-only output, invalid plan/draft rejection, requested repeat/redaction and the actual memory-only dispatcher reporting two calls and persisting accepted notes without world changes. ### Conversation-thread journal prototype (2026-10-17; NOT deployed)

The reported romance → delegated choice → epic-scale exchange is a continuity/delivery failure, not a request for a larger biography. Existing `npcNaturalHistory:<adventure>:<npc>:<player>` already holds eight accepted exchanges. Reuse it; do not add a parallel interaction file, promote old utterances to facts, or reintroduce an assessor/writer/judge loop. The candidate projects all eight eligible turns (oldest projected dialogue may be trimmed to retain the existing24k-character request budget), retains withdrawn-source redaction, and supplies recent player requests, the last utterance and the latest valid thread together with the fresh factual source sheet. No actual saved history is removed by prompt trimming.

For the one-pass writer, speech/fiction now generate a bounded `thread` before their prose in the SAME response: `{request, choices, move}`. `request` identifies the current conversational task (max240 characters), `choices` contains up to four selected preferences (max100 characters each), and `move` is respond/deliver/clarify/revise/close/repeat. These are fallible AI interpretation notes, not proof of delivery, world knowledge, permission, a relationship effect or verified memory. The model must distinguish offering to do something from actually doing it, carry selected preferences through short answers and replace the thread when the player changes subject. No genre/action keyword parser extracts these notes. Four-field responses remain compatible with existing diagnostic adapters; the production speech/fiction schema requests the thread. Read/social capability branches retain their existing shapes and authorization.

An exact repeated line with a valid thread and a move other than explicit repeat uses the EXISTING single repair allowance; it cannot start an additional retry/reviewer chain. A requested repetition remains possible. This cheap duplicate check cannot determine whether two different strings mean the same thing, or prove the model correctly chose repeat. It is not a semantic conversation judge.

Accepted notes and `utteranceKind` are saved with the visible reply through the existing atomic publication path, under the same per-player/NPC/adventure scope. Malformed notes are rejected; notes tied to withdrawn evidence are omitted with the old reply. Nothing is added to canonical world/social biography. `kind=fiction` permits clearly framed invented tales, not invented personal anecdotes. Subsequent prompts mark those utterances fiction-only; last-reply diagnostics show the utterance kind. Existing saved replies without a kind remain unverified dialogue, not automatically labelled fiction. Both channels retain display/consequence guards and cannot carry tool IDs/effects. These text guards can still reject an innocent fictional phrase resembling a game consequence; do not loosen global world-state protection to accommodate it.

Live evaluation found that raw history plus stronger instructions was insufficient: it could still repeat verbatim and invent a real experience. A typed-thread six-turn candidate also repeated before the cheap duplicate guard was added, mislabelled some tales as speech and produced unsupported food/escort claims. Therefore this remains a LOCAL PROTOTYPE, not a proven quality fix or rollout approval. A final seeded delegated-choice check delivered a romantic tale in one call, but still selected speech rather than fiction. Structural/authority regressions are not semantic acceptance. Continue using explicit memory-only `nima-fiction` and held-out `selka-fiction` evaluator scenarios; require repeated natural multi-turn acceptance, accurate fiction provenance and acceptable latency before deployment. The loaded model during these tests was Huihui-Qwen3.5-9B-abliterated.Q5_K_M, not the earlier coder; no model/configuration was changed. Main/save data are untouched.

### Review reliability package (2026-10-17; candidate only)

The live conversation path now stages accepted natural history until a short synchronous SQLite savepoint publishes the visible reply together with private history, shared topic memory, active partner, offer and status. No transaction is held across model inference. A per-database/per-party/player in-flight guard rejects a second NPC turn explicitly without starting another generation or overwriting the first progress record. Distinct players can converse concurrently; shared topic history is reloaded at publication so both entries survive. This is single-process app protection, not a distributed turn queue. Failure diagnostics remain separate from accepted narrative memory.

Delayed replies also check current party membership, active adventure and a persisted adventure epoch changed on adventure selection/reset, in addition to canonical location/revision/hearing. Switching away and back or resetting to the same location cannot make an old draft current again. Guarded or stale drafts do not enter accepted history. The experimental personal-story store remains unconnected: this package atomically saves the EXISTING dialogue history, not improvised biography.

Related review fixes: visible chat selects the newest250 entries then restores chronological order; encounter/portrait disclosure uses all eligible speaker encounters independently of that display window and retains private-event filtering. Host-only controls cover character deletion/move, library adventure selection, story resets and application restart, using the same loopback/Host/Origin boundary as AI administration; ordinary LAN login/play remain available. Empty successful provider content is classified invalid-output. Unarmed attacks resolve fixed damage without an impossible0d1 request, including recovery of older pending zero-dice rolls.

Removed only the unreachable resolveLanternSpeech handler, unused currentDmModelProfile alias and unused SkipModelWarmup launcher switch. The legacy assessor/planner/reviewer remains necessary for NPCs not opted into one-pass. Failed prompt variants remain explicit diagnostic baselines under scripts, not runtime imports or default modes. No new AI judge, model switch, runtime anecdote rollout or claim of improved prose quality is included.

### Experimental transactional memory store (2026-10-17; NOT runtime integration)

`scripts/lib/personal-story-store.mjs` is an explicitly constructed SQLite adapter tested only on temporary databases. Nothing imports it into the game dispatcher/startup and no real-save migration is run. Separate prototype tables store scoped typed ledger snapshots with revisions and publication-id receipts. A trusted caller supplies a previously accepted reply and validated memory intent; this adapter does not semantically assess prose or extract memories from it. It fixes event authority/owner and player-only visibility, so hearing markers do not falsely imply every player heard a personal story.

Within a SQLite savepoint, a publication validates active party/adventure membership, matching policy, expected memory revision and the registered adventure's actual canonical-world snapshot hash; writes the memory/hearing update; inserts the actual game event; and records the retry receipt. Failure at any step rolls everything back, including an event inserted before a receipt failure. Outer transactions remain authoritative. A repeated identical scoped publication ID returns the original event/revision; reusing that ID for different content fails. A stale writer or competing SQLite write lock fails without an automatic retry or new model call. Caller orchestration may reload after conflict, not silently overwrite or regenerate biography.

Preparation persists unheard stories without fake audience markers; reopening a temporary disk database preserves provenance and private hearing flags. Stored snapshots are revalidated by the pure ledger, including scope/policy/provenance. Corrupt data is rejected and left intact, not silently reset. No item, quest, reward, world-state, verified-event or biography mutation API is exposed. Scope IDs are database party/adventure IDs; canonical snapshot lookup resolves through the existing adventure registry, not an invented parallel world key.

Limitations: this is NOT connected to asynchronous inference, final dispatcher guards, conversation-history/disclosure storage, multiplayer publication, restart/reset cleanup or policy migrations. Trusted runtime integration must recheck NPC presence/eligible knowledge, current player/scene, model turn ownership and guards before this narrow transactional boundary. Prototype player-private events do not establish a final public dialogue design. Receipt retention and migration lifecycle need a reviewed production plan. No automatic AI preparation generator, new judge layer, live-model quality claim, deployment or service restart is included.

### Capability-specific schema and format ablation (2026-10-17; candidate, NOT deployed)

The ordinary protocol previously allowed an output that combined speech with arbitrary IDs and a global social skill. Real probes produced a family answer with ids=['Maren']/approach='Intimidation': invalid for speech, yet permitted by the broad schema. The fix describes only valid alternatives: speech with empty IDs/method; read with current read IDs and empty reply/method; one branch for each real social goal with its own ID/allowed methods and no success prose. Repairs use a speech-only schema. Runtime validation is retained, not replaced by confidence in a provider's grammar. This is a global protocol correction, not a conversation phrase rule.

The [official llama.cpp grammar guide](https://github.com/ggml-org/llama.cpp/blob/master/grammars/README.md#json-schemas--gbnf) documents schema-constrained generation, notes that the schema is not automatically inserted into the prompt, and warns against mixing object properties and oneOf at the same level. We use complete oneOf object branches. Native selected-server speech/read/social smoke tests all encoded valid branches; this checks compatibility, NOT semantic goal choice. Existing transport/messages/options are preserved; diagnostic generateText is explicit and never an automatic fallback from failed structured generation.

`scripts/probe-dialogue-format.mjs --live --case=family` compares seven bounded isolated drafts. Cases: family, visits, joke, memory, or all. Variants: production, chat-schema, chat-json, chat-text, scene-schema, scene-text, chat-anchored, or all; `--repeat=2` (max3). Source and history digests identify matching inputs; estimated tokens and per-request timing/format validity do not claim semantic success. ## Ownership and turn sequence

| Stage | Responsibility | Allowed output |
| --- | --- | --- |
| Listener | Code resolves actual presence/hearing and selected partner | One current NPC, or honest ambiguity |
| Catalogue | Code filters that NPC's current knowledge and prerequisites | Eligible IDs; public text; guarded subject labels |
| Interpretation | AI reads meaning, recent conversation and available knowledge | Up to three goals, selected knowledge IDs, optionally one authored social goal/approach |
| Validation | Code checks structure, IDs, size and disclosure classes | An accepted proposal, never invented facts |
| Social adjudication | Code checks stakes, approaches, current evidence, retry locks and party blockers | Real check or authored automatic/refusal outcome |
| Performance | AI answers in character from the selected evidence | Proposed speech with evidence citations |
| Review/publication | Independent AI review plus code's structure/claim/context checks | Accepted speech or safe prepared fallback |

No model output is executed as code. No output field can supply a flag, item, route, relationship delta, DC or resolved die roll. Context is checked again after asynchronous inference; moving or changing canonical state while a response is being prepared discards stale prose instead of publishing it in the new scene.

## What the model can understand

Interpretation is semantic and contextual. There are no new expression-specific rules for stomach noises, finding one's feet, a sister's occupation or a hesitant request for working drafts. The model receives the question and can choose whichever reviewed knowledge answers it. Examples used in tests include:

- “My stomach is making more noise than the expedition bell. Any bright ideas?” => advice about existing food destinations, not a purchase.
- “Who helped make you the person standing here?” => potentially Nima's public upbringing/family, without requiring the word *family*.
- “Does she take after you?” => use the previous conversation to identify the sister, then answer only from current family evidence.
- A question about both work and food => separate goals and relevant evidence for each.
- A paraphrased request for unpublished drafts => propose the existing Lethriel social situation, not a new check invented by the model.

These examples are evaluation cases, not production string mappings. Scripted test transports prove the routing and safety boundary; only live model evaluation demonstrates semantic performance. An abstract question may legitimately warrant clarification rather than the author's preferred interpretation.

The model cannot invent another relative, address, tragedy, visitable location or family quest because the player asks an unsupported question.

```json
}
```

Goal kinds are `chat`, `advice`, `detail`, `solution`, `transaction`, `social-check`, `clarification`. These are broad operational meanings, not per-sentence branches. A plan contains one to three goals, at most three IDs per goal and six total references. Every selected ID must exist in the current catalogue. The requested generation schema dynamically enumerates those IDs and the NPC's actual challenge IDs; residents without authored checks are not offered the social-check kind or an approach. This prevents the ambiguous word “social” from inviting a model to treat ordinary family chat as a consequential action. Detail requires a detail/solution goal; solution text requires a solution goal. This checks structural consistency, not mathematical proof that the model correctly understood the player's intent. Independent relevance review remains essential before speech is shown.

A social plan names one current authored challenge and one standard approach. Code then applies the same fixed DC, allowed/forbidden approaches, prerequisites, evidence bypass, actor-specific retry signature, party blockers and atomic persistence used previously. An AI interpretation of ordinary explanation suppresses the old keyword social matcher rather than accidentally requesting a roll. Essential authored interactions and actual physical commands retain their existing engine authority. Multiple simultaneous consequential goals are not supported: one social outcome takes precedence, and ordinary follow-up may be needed for other subjects.

## History and privacy

History is capped at the last six exchanges in prompts and eight persisted exchanges per player/NPC/adventure. Player speech, prior generated replies and knowledge text are labelled untrusted data, not instructions or new authority. Earlier replies whose cited knowledge has been withdrawn are replaced with an unavailable-history marker before semantic planning/performance. Current eligible knowledge, not a past promise or player assertion, supplies truth.

The selected listener, presence checks and per-player history remain unchanged. The model cannot switch speakers, search another resident's private background or import another player's social state. Actual current weather, time, prices and distant NPC whereabouts are unknown unless explicitly authored. Stable observations about sun/shade are not a weather simulator.

## Failure behaviour and diagnostics

- Invalid JSON, unknown IDs, extra fields, wrong disclosure class, duplicate references, invented social goals and excessive output reject the interpretation.
- Model outage or interpretation rejection uses existing bounded matching/authored fallback, not world improvisation. The UI identifies that degraded understanding path.
- Invalid performance or a negative semantic review falls back. Guarded detail/solution text is deliberately excluded from the prepared fallback, so a wrongly selected spoiler cannot leak merely because review rejected the generated answer.
- A purchase request can receive advice/refusal, never a fictitious transfer. Ordinary recommendations do not receive purchase refusals on the semantic path.
- A changed scene/world revision while inference runs aborts publication/adjudication and asks the player to speak again in the current scene.
- Oversized catalogues fail closed; they are not silently truncated so that constraints disappear.

`npcDialogueStatus` records reply source separately from interpretation source/reason. The model menu shows **Understanding: AI interpreted your conversation** versus fallback matching, alongside generated/grounding-checked versus prepared/rules reply status. Private prompt traces use the existing redacted inspector. Rejected drafts and planner instructions do not enter story narration.

## Budgets, latency and scale

The initial planner permits at most 80 available entries and a 24,000-character input packet. The existing model-profile context-budget check can impose a smaller limit. Recent speech/replies are bounded individually. Interpretation uses temperature zero, at most 260 generated tokens and a 75-second timeout to accommodate cold local inference; performance and independent review retain their 45-second per-stage budgets. An empty goal list is invalid both in the generation schema and the runtime validator.

Ordinary live dialogue currently requires three sequential model calls. This is a correctness/flexibility pivot, not a speed improvement; local hardware/model speed and rejection rates must be measured. Do not conceal timeouts as successful AI understanding. Potential next optimisation is a combined interpretation/public-knowledge performance pass, retaining separate review and separate retrieval for guarded details. Do not remove independent validation just to improve a benchmark.

Large-city scale should use reviewed knowledge indexing and scoped retrieval, not an ever-growing full-world prompt. Persistent memories remain engine-confirmed episodes; the model does not write remembered facts from chat. Dynamic schedules, live weather, procedural quests, arbitrary services and unrestricted social actions remain separate designs.

## Verification and rollout

`tests/ai-conversation-planner.test.mjs` exercises injected structured interpretation through actual game/database dispatch: paraphrases, multi-goal selection, all three model stages, pronouns/history, withdrawn knowledge, mismatched disclosure classes, malicious output, rejected spoiler fallback, real social checks/failure/retry/boundaries, ordinary explanation, degraded operation, budgets and stale context. Existing NPC, combat, movement, save and adventure regressions remain required.

`scripts/evaluate-nima-conversation.mjs --live`, run from the configured app checkout, evaluates semantic paraphrases, reference resolution and a work/food question through the real configured transport and prompt budget. It prints source, goals, rejection reason, replies and latency. It does not touch gameplay databases, settings or model loading. This is opt-in because it performs inference on the configured server.

Deploy only after the full test suite, production build/typecheck/portrait checks and adventure validation pass. Merge the isolated branch to GitHub main, rebuild the usual checkout, refresh the existing 4173 process and verify its running commit. Preserve current saves, Nima position/history, art, AI configuration and unrelated local edits. Human acceptance: continue with Nima, try unfamiliar wording and change subjects naturally; inspect the model menu if a reply feels canned. Then expand individual reviewed biographies and evaluate contrasting personalities before adding more districts.

Model interpretation and semantic review can both be wrong. IDs, prerequisite filters and absence of arbitrary write fields constrain authority, but do not prove every sentence true or every social intention correctly understood. Report ambiguity, unwanted checks, repetition, hallucination, source and latency; improve the general interpretation/knowledge contract rather than adding another exact-phrase exception.

### Recorded release evidence (16 October 2026)

392 automated tests pass, with production build/typecheck, 36 portrait checks and all four adventure validations. Initial read-only live runs on configured Tiel-Coder-35B-A3B-UD-IQ4_XS exposed timeouts, empty goal lists and an invented family challenge when the original protocol used the ambiguous label `social`. Those attempts were rejected, not published as successful interpretation. The release protocol uses mandatory nonempty goals, dynamic current-ID enums and the explicit `social-check` class, absent for residents without authored checks.

The final bounded live smoke test asked “Who helped make you the person standing here?” without the word *family*. AI selected Nima's personal/family knowledge and generated a newly phrased answer about her parents' repair-first upbringing and sister Maren's clothes-mending; independent review accepted it. Stage times were 36.5 seconds interpretation, 34.5 seconds performance, 17.0 seconds review: **88 seconds total**. This records one successful final-protocol turn, not a claim of comprehensive multi-turn/model/personality quality. Earlier runs that degraded to fallback are not counted as passes. Human playtesting and latency optimisation remain the immediate next gates; --limit=1 supports a bounded read-only smoke run.
